== Annahmen und Abhängigkeiten
- Das Entwicklerteam hat Vorerfahrung mit Webentwicklung.

== Entscheidungen, Nebenbedingungen und Begründungen

* **Frontend-Framework:** React Native in Kombination mit Expo ermöglicht schnelle Entwicklung, Testing und Deployment auf mehreren Plattformen.
* **Styling:** TailwindCSS (über Nativewind) sorgt für einheitliches, modernes Styling und produktive Entwicklung von UI-Komponenten.
* **Navigation:** Implementierung mit Expo Router für eine flexible und modulare dateibasierende Navigationsstruktur innerhalb der App.
* **Datenhaltung:** In der ersten Version ausschließlich lokal (z.B. AsyncStorage, Expo-SQLite mit Drizzle ORM).
* **Backend:** Noch nicht umgesetzt, Anbindung an REST API vorgesehen.
* **Plattformstrategie:** Fokus auf plattformübergreifende Nutzung (iOS, Android) ohne spezielle Hardwareabhängigkeiten.
* **Testing:** Nutzung von Expo-Tools und Jest für einfaches Testen und Debugging.

== Schichten oder Architektur-Framework

Die Anwendung folgt einer **mehrschichtigen Architektur (Layered Architecture)** kombiniert mit **Domain-Driven Design (DDD)** Prinzipien:

=== Präsentationsschicht (Presentation Layer)
* **Verantwortlichkeit:** Darstellung der Benutzeroberfläche und Interaktion mit dem Benutzer
* **Technologie:** React Native Komponenten, Expo Router für Navigation
* **Dateiort:** `/src/app/`, `/src/components/`
* **Komponenten:**
** Screen-Komponenten für verschiedene Ansichten (Home, Transactions, Budget, etc.)
** Wiederverwendbare UI-Komponenten (Buttons, Modals, Input-Felder)
** Container-Komponenten für komplexe UI-Logik

=== Geschäftslogikschicht (Business Logic Layer)
* **Verantwortlichkeit:** Geschäftslogik, Datenvalidierung und -verarbeitung
* **Technologie:** TypeScript, React Hooks
* **Dateiort:** `/src/db/queries/`
* **Komponenten:**
** Custom Hooks für CRUD-Operationen (useTransaction, useCategory, useBudget, useAccount)
** Geschäftslogik für Berechnungen (Saldierung, Budget-Tracking)
** Validierungslogik

=== Datenzugriffsschicht (Data Access Layer)
* **Verantwortlichkeit:** Abstraktion der Datenbankzugriffe, Schema-Definition
* **Technologie:** Drizzle ORM, Expo SQLite
* **Dateiort:** `/src/db/schemas/`, `/src/db/migrations/`
* **Komponenten:**
** Schema-Definitionen für alle Entitäten
** Datenbank-Migrationen
** Relationen zwischen Entitäten

=== Infrastrukturschicht (Infrastructure Layer)
* **Verantwortlichkeit:** Externe Integrationen und Hilfsfunktionen
* **Technologie:** verschiedene externe APIs und Utilities
* **Dateiort:** `/src/utils/`, `/src/api/`
* **Komponenten:**
** KI-Integration (Gemini API für Belegscan)
** Storage-Utilities (AsyncStorage-Wrapper)
** Mehrsprachig (i18next)
** Helper-Funktionen

**Designprinzipien:**
- **Separation of Concerns:** Jede Schicht hat eine klar definierte Verantwortlichkeit
- **Dependency Inversion:** Höhere Schichten hängen von Abstraktionen niedrigerer Schichten ab, nicht von Implementierungen
- **Single Responsibility:** Jede Komponente/Modul erfüllt genau eine Aufgabe
- **DRY (Don't Repeat Yourself):** Wiederverwendbare Hooks und Komponenten vermeiden Code-Duplikation

Die wichtigsten Komponenten innerhalb des Frontend-Containers sind:

- **Layout-Komponente (`_layout.tsx`):**  
  Steuerung der globalen Navigationsstruktur (z.B. Tab-Navigation).
- **Tabs-Komponenten:**  
  Organisieren die verschiedenen Hauptbereiche der App (z.B. Dashboard, Neue Transaktion, Statistiken).
- **Screens:**  
  Einzelne Ansichten zur Erfassung und Darstellung von Daten, wie Transaktionsübersicht, Kategorien, Konten, Badges etc.
- **Service-Komponenten:**  
  Kapseln die Datenhaltung (zunächst lokal, später via API).
- **Datenmodelle:**  
  Repräsentiert durch die im ER-Diagramm dargestellten Entitäten:  
  Account, Currency, TransactionGroup, Transaction, Category, CategoryTerm, Budget
